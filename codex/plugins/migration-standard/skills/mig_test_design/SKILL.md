# Test Spine — viewpoints, rules, pipeline

> Prerequisite: `mig_project` resolved. This skill holds what UT, IT, automation, review
> and triage all share. The phase skills hold what differs.

Expected values come from the **legacy system**, never from the new implementation
(`references/rules/common/testing.md`). That rule outranks everything below.

---

## 1. Viewpoints, each bound to a technique

A viewpoint without a technique degenerates into "think of some cases". The technique is
what makes coverage arguable and reproducible.

| ID | Viewpoint | Technique | What it forces you to enumerate |
|---|---|---|---|
| VP-01 | Happy path | Scenario-based | the complete business flow, start to finish |
| VP-02 | Empty result | Equivalence partitioning | the empty set as its own partition |
| VP-03 | Validation | Equivalence partitioning + boundary value analysis | field state per mode, input partitions, output correctness, error partitions |
| VP-04 | Auth failure | State transition | authenticated → expired → redirected |
| VP-05 | Repeated submission | State transition | enabled → locked → re-enabled |
| VP-06 | Server / network error | Error guessing | environment failures the UI must survive |
| VP-07 | Cross-module navigation | Scenario-based | drill-down, forward, back, and state on return |
| VP-08 | Permission | Equivalence partitioning | one partition per role |
| VP-09 | Layout integrity | Checklist-based | fixed UI criteria per surface |

Enabled set comes from `{{profile.testing.viewpoints}}`. Disable one only when it cannot
apply — a batch job has no VP-05 — never to reduce effort.

**VP-03 is the largest and the one that decides quality.** It splits four ways:

| Sub | Covers |
|---|---|
| VP-03a | item state — enabled, read-only, visible, per screen mode |
| VP-03b | input data — min, max, min−1, max+1, character class, type |
| VP-03c | output data — displayed values come from the right source; option count *and* content |
| VP-03d | error — over boundary, wrong character class, wrong date format, business constraint |

Migration note: VP-03b and VP-03d boundaries come from the **legacy field definition**, not
from the new UI's `maxlength`. The new UI is what you are testing.

## 2. Mandatory writing rules

**TR-SE01 — steps and expected results are concrete.** Never "enter valid data", "check the
screen displays correctly". Name the field, the value, the control, the observable result.
A step a new tester cannot execute without asking a question is not a step.

```
✗  Enter search conditions and press search
✓  Enter 2026/04/01 in 入荷予定日(From), leave 入荷予定日(To) empty, press 検索
   → grid shows 3 rows, first row 伝票番号 = D-000123
```

**TR-DR01 — cross-check every expected result against the data rules.** Field length,
type, rounding, sort order and default value in the expected result must match the data
design. An expected result that contradicts the data design is a defect in the test, and
it will be argued about during execution instead of before.

**TR-DD01 — no duplicate coverage.** Two cases that differ only in irrelevant input are one
case. Before adding a case, name what partition or boundary it adds that no existing case
covers. If you cannot, do not add it.

**TR-AT01 — split a case when its expectations have different automatability.** A single
case that mixes "grid shows 3 rows" (automatable) with "print output is legible"
(manual) can be neither automated nor cleanly reported. Split it.

**TR-PC01 — preconditions are numbered, executable steps.** Not a prose paragraph. The
tester must be able to reach the starting state by following them in order.

**TR-SC01 — one repeated-submission case per primary action**, not per button on the
screen.

**TR-NE01 — one server-error case per screen**, not per endpoint. The behaviour under test
is the UI's response to failure, which does not vary per endpoint.

**TR-CF01 — confirmation, success and redirect are one case, not three.** For any
create/update/delete: confirm dialog → success feedback → where the user lands. Testing
them separately triples the count and tests nothing extra.

**TR-L01 — language and terminology** follow `{{profile.language.by_path}}` for the
destination, and label text is quoted exactly as the UI shows it.

**TR-ID01 — case ids** follow `{{profile.ids.test_id_format}}`, are unique within a file,
and are never renumbered once the file has been reviewed. Superseded cases are marked
removed, not deleted, so results from earlier rounds stay attributable.

## 3. The checkpoint pipeline

UT and IT are both generated by a multi-step pipeline with human pauses. The shape is
shared; the steps differ.

```
analyse sources ──▶ ⏸ human answers open questions
        │
        ▼
final analysis ──▶ checklist ──▶ ⏸ human reviews coverage
                                        │
                                        ▼
                            write cases ──▶ self-review loop ──▶ done
                                                  ▲     │
                                                  └─────┘  bounded
```

**Why the two pauses exist.** The first buys the answers that stop invention: questions the
sources genuinely do not answer (`NI-01`). The second buys coverage review at the cheap
stage — a missing flow costs one line in a checklist and a full rewrite once cases are
detailed. Removing a pause removes the review it was there to buy.

`{{profile.testing.pipeline.human_pauses}}` says which pauses this project keeps.

**Checkpoint files.** Every step writes a timestamped file under
`{{profile.testing.paths.testcase_root}}/{module dir}/{{profile.testing.paths.step_subdir}}/`.

- timestamp format `{{profile.testing.naming.timestamp}}`
- a later step reads the **newest** file of the prefix it needs
- a retry writes a new file; it never deletes the old one
  (`{{profile.testing.pipeline.keep_retry_history}}`) — the history is how a disputed case
  is traced back to the answer that produced it

**Bounded self-review.** The final step reviews and fixes its own output, at most
`{{profile.testing.pipeline.max_review_rounds}}` rounds. Still failing after that is not a
test-writing problem — escalate it, see `mig_test_review`.

## 4. Case table format

| Column | Rule |
|---|---|
| TC ID | `{{profile.ids.test_id_format}}`, unique, never renumbered |
| Viewpoint | one of the enabled VP ids |
| Priority | High / Medium / Low, justified by business impact not by effort |
| Precondition | numbered steps (TR-PC01); shared preconditions stated once per flow |
| Step | numbered, one action each, concrete (TR-SE01) |
| Expected result | numbered to match, observable, concrete, checked against data rules |
| Legacy anchor | `LEG-*` or `path:line`, or blank for structural expectations |
| Automatable | Yes / No / Partial — drives TR-AT01 splitting and automation scope |
| Result columns | `{{profile.testing.rounds.columns}}` × `{{profile.testing.rounds.count}}`, left **empty** in the design |

Result columns stay empty until execution. A design document delivered with results filled
in cannot be distinguished from one where execution was skipped.

## 5. Coverage arithmetic

Two numbers decide whether a test set is done, and they are checked separately:

| Check | Assertion | Owner |
|---|---|---|
| T-01 | every function design has ≥ 1 case | UT |
| T-02 | every error row in the function design has a case naming its MSG-ID | UT |
| T-03 | every screen flow in the transition diagram has a scenario | IT |
| T-04 | every endpoint appears in ≥ 1 scenario | IT |
| T-05 | every expected value is anchored or structural | both |
| T-06 | every enabled viewpoint appears for every module where it applies | both |
| T-07 | no case duplicates another case's partition (TR-DD01) | both |

T-06 is the one usually missed: a module can have 40 cases and still have zero for VP-08
because nobody asked which roles exist.

## 6. Migration-specific hazards

The defects that survive into production in a migrated system cluster here. Every one of
them is a VP-03 or a data-rule question, and none of them is visible from the new UI alone.

| Hazard | Case to write |
|---|---|
| Rounding and precision | a value whose legacy result differs from naive arithmetic |
| Truncation | input at the legacy maximum, and one character over |
| Date sentinels | the legacy "no date" value, displayed and re-saved |
| Two-digit year windows | dates either side of the legacy pivot year |
| Empty string vs null | a field the legacy stored as empty, filtered on |
| Collation and sort | a list whose order differs under a different collation |
| Half/full-width, encoding | input in each form, saved and redisplayed |
| Time zone | a timestamp near midnight |
| Implicit ordering | a list the legacy returned unsorted but always in one order |

Where the legacy behaviour is unknown, that is a SPEC-GAP: raise it, do not encode a guess
as an expected result. An expected result invented here becomes the specification that the
implementation is later "fixed" to match.
